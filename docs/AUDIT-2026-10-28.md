# Audit, 2026-10-28

An independent review of the repo after step 1. It covers what the project is, how it works, what was fixed, and a ranked backlog. Items marked **Proposed** need Morgan's approval before they become rules (SRC-04).

## What the project is and how it works

- An Electron + TypeScript desktop app for Windows. The DM window runs on the laptop; the table window goes fullscreen on the projector (D-001, D-002).
- `src/core/`: pure logic. `table.ts` holds the state, patches, save parsing and the player view; `displays.ts` picks the table screen. Unit tested with `node:test`.
- `src/main/main.ts`: owns the state, saves it (debounced 200 ms, write then rename), places the table window and answers IPC. Each window has its own preload bridge.
- `src/renderer/`: the DM page (HTML controls) and the table page (Canvas 2D test grid, text drawn twice for both sides, D-008).
- `e2e/`: Playwright drives the real app under Xvfb: two tests, three app launches.
- Measured on 2026-10-28 in a cloud container: `npm run check` 4 s (unit suite 0.15 s); `test:e2e` 3.5 s with Electron cached, 11 s on the first run (it downloads Electron).

## Fixed in this change

1. **The table window could change the game.** Both windows shared one preload, so the table page could call `patch`, read the full state and see the display list. Now the table window has its own bridge with only `getView` and `onView`. It receives `playerViewOf(state)`, which is built field by field, so DM-only data added later can't leak to the projector by default (D-002). Unit and e2e tests check it.
2. **A file dropped on a window was opened in it.** Electron navigates to a dropped file by default, so a DM image dropped on the table window would have been projected. Navigation and new windows are now blocked. The e2e test fails if the block is removed (checked).
3. **Race in the e2e test "unreadable save".** It read `data-view` once. The table shows "curtain" until the state arrives, so a slow start could fail it. It now waits, like the other checks.
4. **Duplicate unit test.** "returns null with only the laptop screen" was already covered by the placement test. Removed; the case stays asserted there.

## Ranked backlog

Format: priority · work (S under 1 h, M a few hours, L a day or more) · impact · item.

### P1: before maps and fog (step 3–4)

1. P1 · S · high · **Find the laptop screen by "built-in", not "main display".** Today "laptop" means Windows' main display. If Windows makes the projector the main display, the table goes fullscreen on the laptop and the DM window opens on the projector, which would project DM data. Electron reports `Display.internal` for built-in screens. Unverified on Windows: needs one check on Morgan's laptop before relying on it. Also open the DM window on the laptop screen explicitly.
2. P1 · S · medium · **Show save problems in the DM window.** An unreadable save is only logged to a console, which the double-clicked Windows app doesn't show. Morgan would silently start fresh. Show a one-line notice with the kept file's name.
3. P1 · M · high · **One draw function for the table and the DM preview.** D-012 puts a live table preview in the DM window. If both windows draw from the same `draw(ctx, playerView, size)` module, the preview can't drift from what is projected. Build it in step 4 with the preview.
4. P1 · M · high · **Plan the state model before step 3.** `applyPatch` checks each field by hand. Maps, fog and markers will need commands (`apply(state, command)`) in `src/core/`, which give undo and a determinism test for free (GAME-02, GAME-06). Decide this in step 3's design, not after.
5. P1 · S · medium · **Calibration needs physical pixels.** `DisplayInfo` carries only the scaled size. Add `scaleFactor` and physical size in step 2 (already in HANDOFF).

### P2: soon, small

6. P2 · S · medium · **Re-place the table window only when its placement changes.** Every `display-metrics-changed` event (taskbar, scaling) exits and re-enters fullscreen, which may flicker mid-game. At start it is placed twice (`ready-to-show` and `did-finish-load`). Needs a Windows check to confirm the flicker before fixing.
7. P2 · S · medium · **Keep the last 3 saves.** Rotate `table-state.json` backups so a bad state can be rolled back, not only an unreadable file. Becomes high once fog and markers exist.
8. P2 · S · medium · **Curtain hotkey.** One key (like PowerPoint's B) blanks the table instantly from the DM window.
9. P2 · S · low · **CI: bump `actions/checkout` and `actions/setup-node` to Node 24 pins** (already in HANDOFF). Use the `efficient-github-actions` skill.
10. P2 · S · low · **CI: cache the Electron binary** (`~/.cache/electron`, keyed on the Electron version). Estimate: saves the download on each run, about 5–10 s (estimated from the local first-run difference).
11. P2 · S · low · **Remove `Bash(npm run lint)` from `.claude/settings.json`.** There is no lint script. Recommendation: don't add ESLint yet; strict TypeScript and Prettier cover this code size.

### P3: later or only if needed

12. P3 · S · low · **CI runs twice per change**: once on the PR and again on `main` after the squash merge. The second run catches a merge that is green alone but red combined. Keep it unless Actions minutes run short.
13. P3 · S · low · The Windows build re-runs `npm run check` (about 10 s). Keep: it stops a zip being built from a red branch.
14. P3 · M · medium · **Fake-display test seam.** Under Xvfb the app sees one screen, so the fullscreen path in `main.ts` is never run end to end. An env var listing fake displays would let one e2e test cover it.
15. P3 · L · medium · Node 22 and Electron 44 support windows: plan an upgrade around April 2027 (Node 22 maintenance ends then).
